## Patterns found

### Tier 1 — Genuine repeated workflows that deserve a skill

#### 1. `docker exec fullstack-fullstack-1 bash -lc "<cd to service> && <test cmd>"` — 65 occurrences

You spend a lot of time running tests inside the dev container. Every variation is the same shape: cd to a service, run that service's test command. Examples:

```
docker exec fullstack-fullstack-1 bash -lc "cd /workspaces/rhythms/railsapi && bundle exec rspec spec/services/..."
docker exec fullstack-fullstack-1 bash -lc "cd /workspaces/rhythms/mlai && poetry run python -m unittest tests..."
```

**Proposed: `/verify` skill.** Detects which service(s) changed from `git diff main --name-only`, runs the right test + lint + typecheck command for each inside the container. Reports pass/fail per service. Replaces the manual docker-exec dance.

**Demo angle:** "You ran this exact shape 65 times in the last few sessions. `/verify` is the skill that did your work for you."

#### 2. `git log --oneline origin/main..HEAD && echo --- && git push -u origin <branch>` — frequent pre-push ritual

You always check "what's about to ship?" before pushing. Sensible. But it's manual.

**Proposed: `/checkpoint` skill** (or fold into `/ship`). Shows commits ahead of main, runs `/verify`, then offers to push. Single command, deliberate gate.

#### 3. State.json manual hand-edits — 6+ direct writes to `.claude/rdev/state.json`

You're hand-writing `cat > .claude/rdev/state.json << 'EOF'` blocks. Old rdev forced this because shell scripts wrote state. The new package's skills auto-init state — but the team won't know this unless you call it out.

**Demo angle:** "You used to do this by hand. The new `/start` skill writes state.json for you. One less ritual."

### Tier 3 — Patterns that already have a skill (validation)

#### `gh api .../pulls/<PR>/comments` — 9 times for PR 5728 alone

Fetching PR review comments. **You already have `/fix-pr` for this.** `/learn` would say: "stop doing this by hand — `/fix-pr` automates it."

This is actually a useful demo beat: show that `/learn` catches when you're *not using* a skill that already exists.

#### `gh run view <id>` — 26 occurrences

Checking CI runs. **You already have `/fix-ci` for the failure case.** For passing CI it's just monitoring; consider a `/ci-watch` skill if this stays painful.
