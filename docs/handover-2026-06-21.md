## What rdev is

A ticket-to-PR pipeline. Two coexisting forms today:

1. **Personal infra** (Ashwin only): tmux + git worktrees + shell scripts (`rstream`, `rbuild`, `rpromote`, `rforward`, `rclean`, `runpromote`) that orchestrate Claude Code sessions in tmux panes. Source: `~/code/rdev/bin/`. Agents at `~/code/rdev/agents/` (builder, coordinator, reviewer). Skills at `~/code/rdev/skills/`.
2. **Harness-agnostic package** (intended for team / external): `~/code/rdev/package/` — installable via `./setup` or planned `npx rdev-init`. Targets Claude Code, Cursor, Codex CLI. Skills + agents + process docs + adapters. Not currently shipped to teammates; an embed-into-rhythms attempt was started and **dropped** mid-2026-06 due to conflicts with existing rhythms `.claude/` content.

User's stance: tmux setup stays personal infrastructure. The skills/agents (the AI orchestration logic) should be shared. Long-term goal: refactor rstream to invoke shared skills internally.

## Open architectural threads (designed, not built)

### 1. Worktree as unit-of-work, local server as routable resource

**Problem.** Today Claude in a worktree runs tests via `docker exec fullstack-fullstack-1 bash -lc "cd /workspaces/rhythms/<svc> && <test cmd>"`. The container mounts the main checkout (`~/code/rhythms`), NOT the worktree. So tests run against main's code while the agent thinks they're testing the worktree. **Silent wrong-code testing happens every day.** It's not loud because most tests still pass; correctness only breaks for branch-specific code.

Three options were sketched:
- **(A)** Quick fix: session-history migration script so moving a session between local/worktree paths doesn't lose Claude history. Doesn't fix the wrong-code problem.
- **(B)** Architectural: docker compose mounts `${RHYTHMS_DIR}` (env var). `rpromote` updates env var to worktree path, `docker compose up -d --force-recreate`. Always-worktrees model. Services follow whichever worktree is "active". Sessions never move (they live in the worktree from creation). Estimated 2-3 hours + compose changes for the team.
- **(C)** Hybrid: keep "local mode" branding but decouple session location from mount target.

User leans (B). **Never picked. Never built.** Status quo: silent wrong-code testing, manual `rpromote` to fix.

### 2. `rlocal` lease system for the live server

**Problem.** Even in option (B), only one worktree can own the live server at a time. Multiple streams need to coordinate.

Designed:
- Lease file at `~/code/rhythms/.rdev/local-lease.json` (`{holder, worktree_path, claimed_at, pid, user}`)
- CLI: `rlocal status / claim / release / wait / queue / force-claim`
- Three modes when not lease-holder: **wait** (block agent), **queue** (FIFO, async notify), **container-free** (run tests via mise + native, no docker)
- Integration: `rpromote` calls `rlocal claim` internally; skills check `rlocal status --json` before docker exec; failure surfaces three-option prompt

Two open design decisions before building:
1. **Lease granularity** — one big lease for whole stack vs per-service? (Recommended: one big lease.)
2. **Stale policy** — auto-release after TTL vs stay-claimed-until-explicit? (Recommended: stay-claimed + opt-in `--ttl` flag.)

**Never built.** Depends on (1) above.

### 3. `/learn` skill

Self-improvement skill that mines the user's recent activity (Claude session JSONLs, git log, memory files) for repeated patterns and proposes skill drafts.

- Preview already generated from real session data: `~/code/rdev/docs/plans/learn-preview-2026-06-04.md`. Strong real candidates found: `/verify` (docker exec test patterns, 65 occurrences), `/checkpoint` (pre-push ritual), CLAUDE.md additions from existing memory feedback.
- Design: discover → filter against existing skills → present → multi-select via AskUserQuestion → draft only what's selected to `.rdev/proposals/<slug>.md` → user manually `mv` to promote.
- Was Task 6 in the embed-demo plan, which was dropped mid-execution.

**Never built.** Most novel piece of work; would be the "wow" if we ever do a team demo again.

## Tactical loose ends

- **`~/.claude/skills/rdev/` is a one-time copy.** Drifts every time `~/code/rdev/skills/` is edited. Suggested making it a symlink (`ln -s ~/code/rdev/skills ~/.claude/skills/rdev`). User has not yet decided. Workaround: run `cp -r ~/code/rdev/skills/* ~/.claude/skills/rdev/` after any rdev edit.
- **No `LINEAR_API_KEY`** in env or `~/.config/rdev/config`. `rstream` can't pre-fetch Linear's `gitBranchName` itself. The coordinator-side rename works but the placeholder `stream/USENG-XXX` branch is visible until the agent runs (~10s of confusion at start of each stream).
- **Other worktrees may have stale review skills.** USENG-926 was patched manually. Other live worktrees may still have the pre-2026-06-16 review skill calling `codex:codex-rescue`. Check with:
  ```bash
  grep -l "codex:codex-rescue" ~/code/rhythms/.claude/worktrees/*/docs/skills/review/SKILL.md 2>/dev/null
  ```
  For each match: `cp ~/code/rdev/skills/review/SKILL.md <that path>`.

## User context worth remembering

- **Tmux session is named `main`** (not `rdev`) — set in `~/.config/rdev/config`.
- **Each rstream window has 2 panes**: pane 0 = `claude` (coordinator), pane 1 = `zsh` (shell).
- **CLAUDE.md in rhythms is a SYMLINK to README.md** — do not edit "CLAUDE.md" assuming it's separate. Edits land in the public README.
- **`.claude/` is gitignored** in rhythms (`/.claude` in `.gitignore`). Specific files are tracked via `git add -f` (settings.json, the skills symlink, etc.). Most of `.claude/` is local-only.
- **`.claude/skills` in rhythms is a SYMLINK to `../docs/skills`**. Skills physically live at `docs/skills/`. `.agents/skills/` is the team's tracked skills location (per `.gitignore`: `.agents/*` ignored, `!.agents/skills/` exempted).
- **User runs `rclean`, `rpromote`, `rforward` from his zsh** — `~/.local/bin/<name>` is a symlink to `~/code/rdev/bin/<name>`. Editing files via symlink fails on Write tool; use Edit, or resolve symlink first.
- **The `rpromote` shell-function wrapper in `~/.zsh_aliases`** auto-`cd`s to `$RHYTHMS_DIR` after the script runs (because the worktree dir is deleted out from under the shell).
- **User prefers terse, direct responses.** No trailing summaries of what was just done; the diff/output speaks for itself. Lean on tables for multi-option comparisons.
- **User's pushback style is signal, not noise.** When he asks "are you actually thinking this through" or "wait, that's not true" — he's almost always right. Verify before doubling down.
- **No history in `~/code/rdev` git repo yet** — there are no commits. Everything is uncommitted on `main`. User has not been committing this work; it's been a working repo.
